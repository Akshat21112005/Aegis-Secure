# AEGIS Secure – Runtime Specialist

# Part 1 – Vision, Motivation & Philosophy

---

# 1. Why Infrastructure Alone Is Insufficient

The Infrastructure Specialist was the first specialist in AEGIS Secure for good reason. Before any browser executes a webpage, the Internet already exposes a rich set of externally verifiable facts: WHOIS registration data, DNS records, TLS certificates, HTTP headers, static HTML source, and JavaScript files as they exist on the wire.

For many phishing websites, especially low-sophistication kits, this static evidence is enough. A domain registered yesterday, a mismatched TLS certificate, a login form pointing to a Telegram bot, and obfuscated JavaScript in the page source often tell a clear story without ever opening a browser.

Modern phishing, however, increasingly depends on **behavior that only appears after execution**.

Attackers learned that static analysis can be evaded. A page can ship with almost no malicious HTML and still become dangerous once JavaScript runs. Login forms can be injected after load. Redirects can happen through `history.pushState`. Credentials can be exfiltrated through `fetch` or `sendBeacon` after a delay. Storage APIs can persist attacker-controlled state. Permission prompts can reveal intent that never appears in source code.

Infrastructure answers a powerful question:

> **What exists before the page is executed?**

It cannot reliably answer:

> **What does the page do once it is alive inside a browser?**

That gap is why Runtime exists.

---

# 2. Static Analysis vs Dynamic Analysis

AEGIS Secure deliberately separates two classes of analysis.

## Static Analysis

Static analysis inspects artifacts **without executing them**.

Infrastructure performs static analysis of:

```text
WHOIS

DNS

TLS

HTTP

Cookies

HTML

JavaScript source
```

The page is treated as data. No code runs. No DOM is created. No network activity is generated by client-side execution.

## Dynamic Analysis

Dynamic analysis inspects a system **while it executes**.

Runtime performs dynamic analysis of:

```text
Executed JavaScript

Live network requests

Rendered forms

Browser storage

Permission states

Console output

DOM mutations
```

The page is treated as a program. The browser becomes the execution environment.

This distinction is fundamental in cybersecurity. Malware analysts do not rely on reading binaries alone; they execute samples inside sandboxes. Runtime applies the same principle to phishing websites.

---

# 3. Why Runtime Exists

During early AEGIS development, Infrastructure was expected to carry most of the phishing-detection burden. After studying contemporary phishing kits, that assumption broke down.

Common runtime-only behaviors include:

* Dynamically inserting login forms after page load.
* Creating forms only after user interaction.
* Loading malicious scripts from remote servers after an initial delay.
* Redirecting through JavaScript instead of HTTP `Location` headers.
* Injecting invisible iframes at runtime.
* Fetching exfiltration endpoints after the page appears benign.
* Opening WebSocket channels for command-and-control style communication.
* Requesting browser permissions unrelated to the visible page purpose.
* Writing tracking or credential data into `localStorage`, IndexedDB, or service workers.

None of these are guaranteed to appear in static HTML or in a single HTTP response. Some never appear at all unless JavaScript executes in a real browser context.

Runtime therefore became necessary as the **dynamic counterpart** to Infrastructure's static observation layer.

---

# 4. How Real Browsers Behave Differently from Static HTML

A webpage is not a document. In a browser, it is an **active runtime system**.

When Chromium loads a URL, it does far more than parse HTML:

```text
Download HTML

Parse DOM

Fetch CSS, images, fonts, and scripts

Execute JavaScript

Apply DOM mutations

Schedule timers

Open network connections

Register service workers

Read and write storage

Handle dialogs and permission prompts

Continue loading indefinitely on SPAs and dashboards
```

The final page state may differ completely from the original source.

Examples:

| Static HTML | Runtime Result |
|-------------|----------------|
| No forms | Fake Microsoft login injected by JavaScript |
| Benign anchor links | `window.open` to credential-harvesting popup |
| Empty body | Entire page built by client-side framework |
| One script tag | Additional scripts inserted dynamically |
| No visible redirect | `history.pushState` changes apparent URL |

Infrastructure sees the left column. Runtime sees the right column.

That difference is not an implementation detail. It is the core motivation for the entire specialist.

---

# 5. The Birth of the Runtime Specialist

Runtime began as a simple idea:

```text
URL

↓

Playwright

↓

Observe

↓

LLM
```

The first prototype launched Chromium, visited a page, and dumped browser events into a prompt. It worked as a proof of concept, but it immediately exposed architectural problems:

* Too many raw browser events for an LLM to consume efficiently.
* Multiple collectors duplicated browser launches.
* JavaScript behavior was invisible without instrumentation.
* Dynamic pages never reached a stable "finished" state.
* Anti-bot systems blocked or altered execution.

Runtime therefore evolved from a script into a **specialist module** with the same layered shape as Infrastructure:

```text
Collectors

↓

Preprocessing

↓

Evidence Builder

↓

Prompt

↓

Predictor
```

The Runtime Specialist was born when we stopped treating Playwright as the product and started treating it as the **execution engine beneath a browser behavior analyst**.

---

# 6. Why Playwright Was Chosen over Selenium

Several browser automation options were evaluated:

```text
Selenium

Playwright

Puppeteer

HTTP requests + HTML parsers
```

Playwright was selected because it best matched AEGIS Secure's engineering needs:

* **Asynchronous APIs** that fit Python `asyncio` orchestration.
* **Multi-engine support** across Chromium, Firefox, and WebKit.
* **Event-driven architecture** for network, console, dialog, and download events.
* **Browser context isolation** for safer, repeatable sessions.
* **First-class storage, permission, and download APIs**.
* **Reliable JavaScript execution** in a real browser environment.
* **Strong developer experience** and maintainability.

The decisive advantage was event-driven collection. Runtime needs to **listen** to browser behavior, not poll the DOM and network on a timer. Playwright's event model made that practical.

Selenium remains viable for many automation tasks, but Playwright aligned better with AEGIS Secure's sensor-based collector architecture and async multi-collector design.

---

# 7. Why Chromium Instead of HTTP Requests

It is tempting to ask why Runtime does not simply issue HTTP requests and parse the response. That approach is fast, cheap, and easy to deploy. It is also **not browser execution**.

HTTP clients do not:

* Execute JavaScript
* Build a live DOM
* Trigger `fetch`, XHR, or WebSocket activity from page scripts
* Populate `localStorage` or IndexedDB
* Register service workers
* Fire timers, dialogs, or permission prompts
* Reveal post-render forms

Many modern phishing pages are effectively empty until JavaScript runs. Some never reveal their malicious behavior without browser APIs.

Chromium was chosen because Runtime's job is to observe **browser truth**, not transport-layer truth. A HTTP response is only the first frame of a much longer execution story.

---

# 8. Runtime as a Browser Behavior Analyst

The correct mental model for Runtime is not "headless browsing." It is **browser behavior analysis**.

Imagine a security analyst opening a suspicious link in a controlled environment. They would watch for:

* Unexpected redirects
* Login or OTP forms that were not in source HTML
* Password fields posting to external domains
* JavaScript errors and console warnings
* Permission prompts for camera, clipboard, or geolocation
* Suspicious network calls after page load
* Downloads triggered without user intent
* Hidden iframes and dynamically inserted scripts

Runtime automates that analyst workflow.

It does not merely visit a page. It observes how the page behaves, compresses those observations into structured evidence, and hands that evidence to a specialist model for reasoning.

---

# 9. Runtime vs Infrastructure

Infrastructure and Runtime are **complementary**, not competing.

| Dimension | Infrastructure | Runtime |
|-----------|----------------|---------|
| Question | What exists before execution? | What happens during execution? |
| Method | Query external services and static artifacts | Execute page in Chromium |
| JavaScript | Read source | Observe runtime calls and mutations |
| Forms | Parse HTML | Inspect rendered DOM |
| Network | HTTP/TLS layer | Browser-generated requests |
| Trust model | Never execute untrusted code | Intentionally execute inside isolation |

Infrastructure observes:

```text
WHOIS

DNS

TLS

HTTP

Cookies

HTML Source

Static JavaScript
```

Runtime observes:

```text
Executed JavaScript

Network Requests

Browser Storage

Permissions

Forms after Rendering

Console Events

DOM Mutations
```

A sophisticated phishing site may look acceptable to Infrastructure while appearing highly suspicious to Runtime, or the reverse if anti-bot systems block dynamic execution. Fusion benefits from both perspectives.

# 10. Design Philosophy

The Runtime Specialist follows the same core philosophy established by Infrastructure.

## Collectors Collect

Every Runtime collector is a **sensor**.

```text
Observe

↓

Normalize

↓

Return Dictionary
```

Collectors do not:

* classify phishing
* compute risk scores
* apply heuristics
* load language models

They only record browser facts.

## LLM Reasons

Intelligence lives above the collectors in:

```text
preprocessing.py

evidence_builder.py

prompt.md

predictor.py
```

The model receives a compact runtime profile, not a firehose of raw browser events.

## Separation of Deterministic and Intelligent Components

This separation is deliberate.

| Layer | Responsibility | Deterministic? |
|-------|----------------|----------------|
| `browser.py` | Browser lifecycle | Yes |
| `behavior/*.py` | Evidence collection | Yes |
| `preprocessing.py` | Compression and normalization | Yes |
| `evidence_builder.py` | Orchestration | Yes |
| `predictor.py` | Reasoning and JSON output | No |

If a collector starts "deciding" whether a page is phishing, the architecture collapses into unmaintainable rules. Runtime avoids that by making reasoning a single responsibility of the specialist model.

---

# 11. Runtime Specialist Objectives

The Runtime Specialist has one primary objective:

> **Assess how trustworthy a webpage appears based solely on live browser execution evidence.**

Secondary objectives include:

* Detect dynamic phishing behaviors invisible to static analysis.
* Produce explainable output through indicators and missing evidence.
* Maintain a standardized JSON interface for Fusion.
* Keep evidence compact enough for small local models.
* Remain independent from Infrastructure, Semantic, and OCR.
* Fail gracefully when navigation or execution is blocked.

Runtime does **not** attempt to make the final system decision. Fusion owns that responsibility.

---

# 12. Threat Model

Runtime assumes the target URL is potentially hostile.

Threats and constraints considered in the design:

* **Malicious JavaScript execution** inside an isolated browser context.
* **Credential harvesting forms** created after page load.
* **Data exfiltration** through `fetch`, XHR, beacon, or WebSocket channels.
* **Social engineering dialogs** and permission prompts.
* **Anti-bot and challenge pages** such as Cloudflare Turnstile.
* **Infinite-loading SPAs** that never reach a stable state.
* **Memory and latency cost** from real browser execution.
* **Incomplete observation** when execution is blocked or redirected away.

Runtime does not attempt to bypass protections, sandbox escapes, or attacker-controlled browser exploits outside its own controlled Chromium session. It records what it can observe and reports limitations explicitly.

---

# 13. Engineering Principles

The following principles guided Runtime design:

1. **One browser, one page, many collectors.**
2. **Attach listeners before navigation when event capture requires it.**
3. **Run independent collectors concurrently with `asyncio.gather`.**
4. **Keep JavaScript instrumentation inside `javascript_runtime.py`.**
5. **Merge network lifecycle events into one collector.**
6. **Compress evidence before prompting the model.**
7. **Never mix orchestration and reasoning in the same module.**
8. **Return the same JSON schema as every other specialist.**
9. **Treat blocked execution as evidence, not as failure to hide.**
10. **Prefer fewer cohesive files over many fragmented modules.**

---

# 14. Why Runtime Became the Second Specialist

Runtime became the second specialist because dynamic browser behavior is the largest blind spot left after Infrastructure.

The priority order was deliberate:

```text
1. Infrastructure — static Internet evidence

2. Runtime — dynamic browser evidence

3. Semantic — message and language evidence

4. OCR — visual evidence
```

Without Infrastructure, the system lacks grounding in domain age, DNS, and transport security. Without Runtime, the system is blind to post-execution phishing behavior. Together they form the technical foundation of AEGIS Secure's multi-agent design.

---

# 15. Evolution of the Architecture

Runtime architecture evolved through several distinct stages.

## Stage 1 — Raw Playwright Dump

```text
URL → Playwright → Dump Events → LLM
```

Problem: token explosion and inconsistent browser state.

## Stage 2 — Multiple Browsers

```text
Each collector launches its own Chromium instance
```

Problem: duplicated execution, high memory use, inconsistent observations.

## Stage 3 — Shared Browser, Sequential Collectors

```text
One page → collectors run one after another
```

Problem: unnecessary waiting and poor CPU utilization.

## Stage 4 — Shared Browser, Async Collectors

```text
One page → asyncio.gather(forms, storage, javascript, permissions, ...)
```

Improvement: lower latency, same browser truth.

## Stage 5 — Frozen Specialist Architecture

```text
browser.py

behavior/

preprocessing.py

evidence_builder.py

prompt.md

predictor.py

evaluate.py
```

This is the final form documented in Parts 2 through 5.

---

# 16. Runtime Philosophy in One Sentence

Infrastructure explains **what the Internet knows about a website before it runs**.

Runtime explains **what the website actually does when it runs inside a real browser**.

That sentence is the philosophical foundation of the entire specialist.
