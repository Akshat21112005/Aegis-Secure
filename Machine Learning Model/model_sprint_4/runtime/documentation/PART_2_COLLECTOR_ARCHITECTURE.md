# AEGIS Secure – Runtime Specialist

# Part 2 – Complete Runtime Collector Architecture, Browser Instrumentation and Collector Design Philosophy

---

# 11. Runtime Specialist Philosophy

Unlike the Infrastructure Specialist, which observes **Internet infrastructure**, the Runtime Specialist observes **browser behavior**.

This distinction became the foundation of the Runtime module.

Infrastructure asks

> **"What exists before visiting the website?"**

Runtime asks

> **"What actually happens after visiting the website?"**

These are fundamentally different questions.

Infrastructure never trusts the webpage.

Runtime intentionally executes the webpage inside an isolated Chromium instance to observe its behavior.

This is similar to how malware analysts execute binaries inside sandboxes instead of simply reading executable files.

The Runtime Specialist therefore acts as a **browser behavior analyst**.

---

# 12. Why Runtime Exists

Initially we believed Infrastructure would detect the majority of phishing websites.

However, after studying modern phishing kits, we realized attackers increasingly use JavaScript to hide malicious behavior.

Examples include:

* Dynamically inserting login forms after page load.
* Creating forms only after user interaction.
* Loading scripts from remote servers.
* Redirecting using JavaScript instead of HTTP.
* Injecting invisible iframes.
* Fetching malicious resources after a delay.
* Using WebSockets for command-and-control style communication.
* Requesting browser permissions.
* Storing data in browser storage.

None of these are visible through static analysis alone.

Therefore Runtime became necessary.

---

# 13. Runtime vs Infrastructure

One of the biggest architectural realizations was that Infrastructure and Runtime are **complementary**, not competing.

Infrastructure observes

```text
WHOIS

DNS

TLS

HTTP

Cookies

HTML Source

Static JavaScript
```

Runtime observes

```text
Executed JavaScript

Network Requests

Browser Storage

Permissions

Forms after Rendering

Console Events

DOM Mutations
```

Infrastructure never executes code.

Runtime always executes code.

---

# 14. Browser-Centric Architecture

The Runtime Specialist revolves around a single object:

```text
Playwright Page
```

Everything depends on the browser page.

Unlike Infrastructure where collectors independently query external services,

Runtime collectors all inspect the same browser instance.

Architecture

```text
Browser

↓

Chromium

↓

Context

↓

Page

↓

Collectors
```

Every collector receives exactly the same page object.

This guarantees

* identical browser state
* identical JavaScript execution
* no duplicate rendering
* no duplicate navigation

---

# 15. Why Playwright?

Initially several browser automation frameworks were considered.

Examples

```text
Selenium

Playwright

Puppeteer

Requests + BeautifulSoup
```

Eventually Playwright was selected because it offers

* asynchronous APIs
* Chromium, Firefox and WebKit support
* event-driven architecture
* browser context isolation
* excellent developer experience
* reliable JavaScript execution
* network interception
* storage APIs
* download events
* permission handling

Most importantly,

Playwright exposes browser events instead of requiring constant polling.

---

# 16. Browser Manager (`browser.py`)

Although very small,

`browser.py` became one of the most important architectural files.

Its responsibility is not analysis.

Its responsibility is lifecycle management.

Responsibilities

```text
Launch Browser

↓

Create Context

↓

Create Page

↓

Navigate

↓

Return Page

↓

Cleanup
```

Nothing else.

It never reasons.

It never collects evidence.

It simply provides an execution environment.

---

## Future Extensions

The browser manager was intentionally designed to allow future capabilities such as

* rotating user agents
* mobile device emulation
* proxy rotation
* stealth plugins
* screenshot capture
* video recording
* HAR recording
* geolocation spoofing

without changing collector implementations.

---

# 17. Collector Design Philosophy

Every Runtime collector follows the same design philosophy as Infrastructure.

```text
Observe

↓

Normalize

↓

Return Dictionary
```

No collector performs

* phishing detection
* confidence scoring
* risk scoring
* manual heuristics

Every collector behaves like a sensor.

# 18. Network Collector (`network.py`)

The Network Collector is arguably the largest Runtime collector.

Question answered

> **"How does this webpage communicate with the outside world after execution?"**

Unlike Infrastructure HTTP,

this collector observes every network event generated by JavaScript.

Examples

```text
Document Requests

Image Requests

Script Requests

Stylesheets

XHR

Fetch

Beacon API

WebSocket

Downloads

Redirect Chains

Third Party Domains

Resource Types

Status Codes

Request Methods

Response Headers

Response MIME Types

Failed Requests

Timing
```

---

## Why Merge Requests and Responses?

Initially we planned

```text
requests.py

responses.py
```

as separate collectors.

After implementation,

we realized they describe the same network transaction.

Keeping them separate only increased complexity.

Eventually

```text
network.py
```

became responsible for the complete request-response lifecycle.

---

## Downloads

Downloads initially had

```text
downloads.py
```

Later merged into network.

Reason

Downloads are simply another network event.

---

## Redirects

Runtime redirects initially had

```text
redirects.py
```

Later merged.

Reason

Redirects are naturally part of the request lifecycle.

---

## Final Responsibilities

The Network Collector ultimately became responsible for

```text
Request

↓

Response

↓

Redirect

↓

Download
```

forming a complete communication timeline.

# 19. JavaScript Runtime Collector (`javascript_runtime.py`)

This became the most technically challenging Runtime collector.

Question answered

> **"What JavaScript behavior occurred during execution?"**

Unlike Infrastructure,

this collector does not inspect source code.

Instead it observes runtime behavior.

---

## Major Difference

Infrastructure

```text
Read JavaScript
```

Runtime

```text
Execute JavaScript
```

Completely different analyses.

---

## Instrumentation

The collector injects lightweight hooks before page execution to monitor selected browser APIs.

Examples include

```text
eval

Function

document.write

window.open

history.pushState

history.replaceState

fetch

XMLHttpRequest

WebSocket

sendBeacon

postMessage

setTimeout

setInterval

atob

btoa

Clipboard APIs
```

Rather than blocking these APIs,

the hooks simply count and record their usage.

This preserves page functionality while exposing execution behavior.

---

## Console Monitoring

Besides API hooks,

the collector records

```text
Console Logs

Warnings

Errors

Unhandled Exceptions

Dialogs
```

These often reveal

* JavaScript failures
* CSP violations
* mixed-content issues
* suspicious runtime behavior

---

## DOM Metrics

After execution,

the collector inspects

```text
Script Count

Inline Scripts

External Scripts

Iframes

Forms

Hidden Inputs

Buttons

Anchors

Password Fields

Images
```

Notice

Runtime DOM metrics differ from Infrastructure HTML metrics because JavaScript may have modified the document.

# 21. Storage Collector (`storage.py`)

Question answered

> **"What information does the webpage store inside the browser?"**

Unlike Infrastructure cookies,

this collector analyzes browser-managed storage.

Evidence includes

```text
Cookies

Local Storage

Session Storage

IndexedDB

Cache API

Service Workers
```

Rather than exposing actual values,

the collector returns

* counts
* names
* sizes
* registration status
* security metadata

This keeps prompts compact while avoiding unnecessary exposure of stored content.

# 23. Runtime Collector Philosophy

By the end of Runtime collector development,

a clear pattern emerged.

Every collector behaved identically.

```text
Observe

↓

Normalize

↓

Return Evidence
```

No collector knew anything about

* phishing
* security scores
* confidence
* machine learning

The Runtime Specialist therefore became

```text
Five Browser Sensors

↓

One AI Runtime Analyst
```

instead of

```text
Five Independent Rule Engines
```

This mirrors the philosophy established by the Infrastructure Specialist while focusing on **dynamic browser behavior** rather than **static Internet infrastructure**.
